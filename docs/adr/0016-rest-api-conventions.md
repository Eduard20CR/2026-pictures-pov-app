# 0016. REST API conventions

- **Status:** Accepted
- **Date:** 2026-10-27

## Context

Every endpoint must look and behave the same so the frontend, the OpenAPI contract (RNF-OPE-06) and the error handling stay consistent. The API has one client, the SPA, deployed together with the backend. Guests have no account; owners, moderators and admins log in with Cognito ([0006](0006-authentication-amazon-cognito.md)).

## Options

| Option | Pro | Con |
|---|---|---|
| Contract-first (write OpenAPI, generate code) | Contract reviewed before code | Two sources to keep in sync; slower for one developer |
| Code-first with springdoc | One source of truth; contract always matches the code | Contract exists only after the code |
| Version in the URL (`/v1`) | Old clients keep working | Unneeded with a single client deployed together |
| No version, backward-compatible changes | Simple URLs | Breaking changes need expand/contract |
| Offset pagination | Simple; jump to any page | Slow on large tables; duplicates when rows are added |
| Cursor pagination | Stable and fast on growing galleries | No jump to page N |

## Decision

**Code-first with springdoc, no version prefix, and the conventions below.** One source of truth for the contract, and the same rules for every endpoint.

| Topic | Convention |
|---|---|
| Contract | Generated by springdoc from the code; frontend types generated with openapi-typescript |
| Versioning | No `/v1`; changes stay backward compatible (expand/contract) |
| Routes | Plural nouns in kebab-case: `/events/{publicCode}/images` |
| Route groups | No prefix: public guest routes. `/me`: resources of the logged-in user. `/admin`: `admins` group only |
| Authentication | `Authorization: Bearer <JWT>` from Cognito on `/me` and `/admin`; guests are identified by their device cookie |
| JSON | camelCase fields; ids as UUID strings |
| Dates | Instants in ISO-8601 UTC with `Z` (`2026-12-05T18:30:00Z`); calendar dates as `YYYY-MM-DD` |
| Errors | RFC 9457 Problem Details (formerly RFC 7807), `application/problem+json`, plus a `code` field in `UPPER_SNAKE_CASE` |
| Pagination | `?limit=&cursor=`; response `{ "items": [...], "nextCursor": "..." }`, `nextCursor` is `null` on the last page |

### Example request

```http
GET /me/events?limit=2
Authorization: Bearer eyJraWQiOi...
```

```json
{
  "items": [
    {
      "id": "3f2b8c1e-7a4d-4e8b-9c2f-1d5e6a7b8c9d",
      "name": "Ana & Luis Wedding",
      "eventDate": "2026-12-05",
      "status": "ACTIVE",
      "createdAt": "2026-10-27T16:45:00Z"
    }
  ],
  "nextCursor": "eyJjcmVhdGVkQXQiOiIyMDI2LTEwLTI3In0"
}
```

### Example error

```http
HTTP/1.1 404 Not Found
Content-Type: application/problem+json
```

```json
{
  "type": "about:blank",
  "title": "Not Found",
  "status": 404,
  "detail": "No event exists with this code.",
  "instance": "/events/q7Xk2mPz9LwR4tVb8NcY1a",
  "code": "EVENT_NOT_FOUND"
}
```

## Consequences

- ✅ One contract, always in sync with the code and the frontend types.
- ✅ The client decides on `code`, not on the `detail` text.
- ✅ Cursor pagination stays fast while guests keep uploading.
- ⚠️ A breaking change needs expand/contract across two deployments.
- ⚠️ No jump to an arbitrary gallery page.
- ⚠️ Authorization inside `/me` is checked per event against the invitations (RNF-SEG-02), not by the route alone.
